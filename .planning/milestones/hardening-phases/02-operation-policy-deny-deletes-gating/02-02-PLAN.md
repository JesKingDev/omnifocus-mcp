Guard block structure (inserted immediately after `const compiled = this.compiler.compile(args);`, before any `if`
branches):

1. Call parseRole() to get the current role.
2. Build the normalized item list:
   - If compiled.operation === 'batch': map compiled.operations[] to { operation: op.operation, target: op.target ??
     'task' }
   - If compiled.operation === 'bulk_delete': produce [{ operation: 'bulk_delete', target: compiled.target ?? 'task' }]
     (the ids are not individually typed, the operation itself is what's denied)
   - If compiled.operation === 'tag_manage': produce [{ operation: 'tag_manage', target: compiled.action }]
   - Otherwise: [{ operation: compiled.operation, target: compiled.target ?? 'task' }]
3. For each item, call decide(role, item.operation, item.target):
   - 'allow' → continue
   - 'deny' → immediately return createErrorResponseV2 with code 'POLICY_DENY_DELETE', message 'Delete operations are
     not permitted for the agent role.', suggestion 'Use complete or drop instead of delete.', details { allowed:
     ['complete', 'drop'], role, operation: item.operation, target: item.target }
   - 'gate' → immediately return createErrorResponseV2 with code 'POLICY_GATE_REQUIRES_OWNER', message 'This structural
     operation requires owner approval before execution.', suggestion 'Re-run from an owner connection using the
     ownerCommand below, or ask the owner to execute it.', details { dryRun: true, preview: { wouldAffect: { count: 1,
     operation: item.operation, target: item.target } }, ownerCommand: { mutation: { operation: compiled.operation,
     ...(compiled as object) } } }

The ownerCommand in the gate response is a copy-paste-ready payload the owner can re-submit from their own OWNER-role
connection — it re-serializes the original compiled mutation args (per D-01 / D-06). Use JSON.stringify(args) or a
reconstructed subset of the original WriteInput as the ownerCommand value.

No changes to Zod write-schema.ts are required — the deny/gate response is a tool output shape, not an input schema
change. The tool description string in OmniFocusWriteTool.ts inputSchema getter MUST be updated to note that delete
operations are rejected for the agent role and structural ops (tag delete/merge) are gated; this is a user-facing
behavior change per the Dual-Schema invariant in CLAUDE.md. </action>

| --------- | ---------------------- | -------------------------------------------------------------------------------------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| T-2-04    | Elevation of Privilege | Funnel bypass — path reaches script builder without guard                              | mitigate    | Guard is the first statement after compile() in executeValidated(). All routing branches (tag_manage, batch, bulk_delete, single) are reached only after the guard passes. Plan 03 adds the script-builder re-assertion as belt-and-suspenders.                                                        |
| T-2-05    | Elevation of Privilege | Batch-parity escape — delete smuggled inside batch/bulk_delete evades single-item deny | mitigate    | Guard walks compiled.operations[] for batch and covers bulk_delete as an operation (not item-by-item by ID). Batch-parity test (OMN-119 lesson) is mandatory and asserts identical deny code across all three surfaces.                                                                                |
| T-2-06    | Elevation of Privilege | Self-approval — AGENT fabricates gate bypass or crafts ownerCommand resubmit           | accept      | D-01: approval = owner re-issuing from a separate OWNER-role connection. | T-2-08    | Denial of Service      | Large batch walks all items before returning first deny                                | accept      | Batch sizes are bounded by Zod schema limits. Walking a batch to find a denied op is O(n) with no I/O — no risk to OmniFocus or the OS. Fail-fast on first deny is preferred; plan implements short-circuit return.                                                                                    |
